# 非确定性排查：按失败的门索引

先看 seamcheck 输出里的**探针**一节，它会直接点名 seek 期间调用过的禁用 API。探针没有点名时，再按失败的门往下查。

## 门 1a 失败（同页面同 t 两次不同）

| 来源 | 特征 | 修法 |
|---|---|---|
| seek 里调用 `Math.random()` | 每次相差几千到几十万像素，探针会点名 | 改用 `hash01(i, frame)` 或固定种子的 `seeded()` |
| seek 里调用 `Date.now()` / `performance.now()` / `new Date()` | 同上 | 所有时间只来自参数 t |
| 每次 seek 都累加的变量（`x += v`、`frame++`、往数组 push） | 差异随调用次数增长 | 改写成 t 的函数；需要积分时用闭式解或缓存（见下文） |
| canvas 没有清空就绘制 | 画面叠加，越画越深 | seek 开头调用 `clearRect` 或铺一层底色 |
| seek 是 async，但内部用 `setTimeout` 延后绘制 | 截图时还没画完 | 返回一个在绘制完成后才 resolve 的 Promise |
| 视频帧：设置 `video.currentTime = x` 后没有等待 `seeked` | 截到的是上一帧 | seek 返回一个等待 `seeked` 的 Promise |
| **CSS 3D 变换层**（`perspective` + `preserve-3d`，镜头通过对整个世界做 translateZ/rotate 实现）：Chromium 选择光栅缩放比例时有滞回，缩放变化不大时会沿用之前的光栅结果，因此输出取决于之前求过哪些 t | 1a、2、5 同时失败，探针不点名；实测相差 1–255 个像素，最大差值 1–21/255。`will-change` 无效 | 每次 seek 用加载期保存的 `#stage` 模板执行 `cloneNode(true)`，整棵替换旧节点，再写入全部样式；canvas 要在新节点上重新 `getContext` 并重绘 |

## 门 1b 失败（重新加载后不同），1a 和 2 都过

这是最隐蔽的一类：同一个页面里那个值始终不变，所以 1a 和 2 都能通过，但下一次渲染时它就变了。实测记录见仓库 docs/verified/film-motion.md。

| 来源 | 修法 |
|---|---|
| 加载时用 `Math.random()` 生成布局或颜色 | 改用 `seeded(固定种子)` |
| 加载时读取 `Date.now()` 作为种子 | 把种子写成常量 |
| 没等字体加载完（用 fallback 字体量出的宽度不同） | 在 `window.ready` 里 `await document.fonts.load(...)`（参见 film-typography） |
| 图片或纹理没等 `decode()` 完成 | 在 `window.ready` 里 `await img.decode()` |
| `fetch` 回来的 JSON 没有在 ready 里 await | 同上 |
| WebGL 精度或驱动差异 | 同一台机器上不应出现；跨机器渲染见"没解决的问题" |

## 门 2 失败（乱序不同），1a 过

| 来源 | 修法 |
|---|---|
| 缓存"上一次 t 的结果"并据此做增量计算 | 缓存只能用来加速，结果必须与从头计算一致。物理仿真用检查点：每 N 帧保存一次状态，seek 时从最近的、时刻不晚于 t 的检查点开始重放（参见 film-physics） |
| 多次 seek 共用同一个 `seeded()` 生成器并持续往下取数 | 每次 seek 内部新建生成器，或改用 `hash01` |
| 复用粒子池，取用顺序依赖调用历史 | 按索引确定粒子身份，而不是按粒子池的顺序 |
| DOM 场景：元素状态（class、style）只在"进入镜头"时设置 | 每次 seek 都把所有相关属性写全 |

## 门 3 失败（循环片）

| 现象 | 修法 |
|---|---|
| 3a 首尾不相等 | 写成 `seek = (t) => paint(wrap(t, D))`，并让动画在 D 处回到起点 |
| 3a 通过但 3b 不通过（首尾相等，但跨接缝处跳变大） | 片尾运动在 D 处的速度与片头速度不一致。周期量用 `2πt/D` 作为相位；弹簧要在 D 之前停稳 |
| 弹簧在 D 处没有停稳 | 用 `spring({ duration })` 反解，保证最后一个关键帧时刻加上 duration 小于 D |

## WAAPI / CSS 动画相关

| 现象 | 原因 |
|---|---|
| 每帧都一样（都是终态） | 没有声明 `USES_WAAPI`，`animations:'disabled'` 把动画 `finish()` 掉了。现在 openScene 遇到这种情况会直接报错 |
| 声明了还是不动 | seek 里没有设置 `anim.currentTime`；或者动画不是 `fill:'both'`，在 0 之前或结束之后不生效 |
| CSS `transition` | transition 由样式变化触发、按真实时间推进，无法按 t seek。改用 WAAPI 并手动设置 currentTime，或者直接在 seek 里计算样式 |

## 门 5 失败（跨启动），门 1–4 都过

门 1–4 都在同一个浏览器进程里运行。门 5 失败说明结果取决于**这一次启动**，而不只取决于 t。分两种情况：

| 现象 | 已知原因 / 排查方法 |
|---|---|
| N 遍之间彼此一致，只有"上次渲染清单"对不上 | 问题出在执行渲染的那个进程里。实测：旧版 headless shell（143/145）在**新安装或新拷贝后第一次启动**时，每个页面开头约 11 帧截成纯白，render.mjs 照样显示 ✓，从第二次启动起恢复正常。重新渲染即可；新安装的旧构建先空跑一次再渲染 |
| N 遍之间不一致 | 先看出现差异的帧是否和整个分片对齐（例如 `1.00–2.00s` 这样的整秒段）。如果是，说明某个页面或浏览器的整体状态不同（字体回退、光栅路径），与场景代码无关；如果不是，说明场景里有和进程相关的输入（读取了系统字体列表、`navigator.*`、没有等待加载完成的资源）。把出现差异的那一帧在两遍里各截一张，解码后比较（`ffmpeg -i x.png -pix_fmt rgba -f md5 -`），对比差异幅度和位置 |
| 只在完整 Chrome（`FILM_CHROMIUM` 指向 Chrome for Testing）下出现 | 实测出现过两次：一次是整片渲染里有 3 个连续分片与其余各次不同（5.7–6.1% 的像素，最大差值 42–174/255）；另一次是门 5 的 30 遍里有 1 遍在 1 帧（分片首帧 t=7.00s）上与其余 5 遍不同（那次的差异幅度没有保留下来，现在门 5 会保存两边的 PNG）。原因尚未查明。默认的 headless shell 在门 5 里跑了 18 遍（ghost-jam 12 遍、demo-tls 6 遍）、整片渲染 10 次，都没有出现过 |
| 片子没有把字体随片打包 | 这不属于跨启动问题，但会让"换构建"看起来像非确定性：缺少字形时会走系统回退，而回退到哪个字体随构建而变（demo-tls 的 `ui-monospace` 出现方块字，最大差值 216/255）。先运行 film-core 的 `scripts/font_source.mjs` |

判断"像素到底有没有变"，始终要**解码后再比较**：换构建或换编码参数时，PNG 字节和 mp4 的 md5 都会变，而像素可能不变（仓库 docs/verified/film-motion.md §11.1）。

## 编码器层的"假非确定性"

两次渲染出的 mp4 md5 不同，并不代表场景是非确定的：实测 H.264 残差噪声会让两次渲染有 46 个像素相差 1–2/255。
判断依据始终在 canvas 层（seamcheck），不要把 mp4 的 md5 当作门。
