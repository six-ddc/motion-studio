# 透视相机 `assets/runtime/camera3d.js`

需要斜着看一个平面时使用。canvas 2D 只有仿射变换，画不出透视，所以这里提供一个针孔相机：JS 侧负责投影点，GLSL 侧按像素反投影回平面，
两边用的是同一组公式。它提炼自片子 `films/weiqi-intro`，实测与该片 `project()` 的结果逐点相差 2.3e-13 px（记录在仓库 docs/verified/film-motion.md §14）。

## 约定

| 参数 | 含义 |
|---|---|
| 世界坐标 | x 向右，y 朝向观众（正俯视时就是画面向下），z 垂直于平面向上。平面为 z = 0（或 z = h） |
| `elevation` | 视线与平面的夹角（弧度），π/2 表示正俯视 |
| `distance` | 相机到注视点的距离（世界单位）。值越小透视越强，趋于无穷时就是正交 |
| `S` | 在注视点处，1 世界单位等于 S 像素（其他深度处再乘以 `k`） |
| `look` / `screen` | 注视的世界点 `[x, y]`，以及它出现在画面上的像素位置 `[X, Y]` |
| `yaw` | 绕 z 轴的旋转（弧度），正值表示画面里的世界逆时针转 |

除 `yaw = 0` 外，这些参数都没有默认值：它们属于镜头决策，由本片决定。`distanceForFov(fovY, S, H)` 可以把竖直视场角换算成 `distance`。

```js
import { camera3d, CAMERA3D_GLSL } from './runtime/camera3d.js';
const cam = camera3d({ S, elevation: follow(t, ELEV), distance: D, look: [9, 9], screen: [L.cx, L.cy] });  // 每帧按 t 新建
const p = cam.project(i, j, 0.25);              // { X, Y, k, depth, behind }
ctx.ellipse(p.X, p.Y, r * S * p.k, r * S * p.k * cam.sn, 0, 0, 2 * Math.PI);   // 平面上的圆 ≈ 椭圆（小圆近似）
fx.render(t, { ...cam.uniforms(), u_wood: ... });  // 着色器里 vec2 w = cam_unproject(cam_px());
```

公式（u, v 为经过 yaw 旋转后的坐标）：`depth = d − v·cos(e) − z·sin(e)`，`k = d / depth`，
`X = sx + S·u·k`，`Y = sy + S·(v·sin(e) − z·cos(e))·k`。反投影求解 `v` 只需解一个一次分式，因此着色器里得到的是**精确逆**；在地平线以上（视线碰不到平面）返回 null 或 `vec2(1e9)`。

GLSL 片段要接在 film-webfx 的 `GLSL.header`（或 `header2`）之后，因为它用到了 `v_uv` 和 `u_res`。`cam_footprint(px)` 给出这个像素在平面上覆盖的宽度（世界单位），远处的细线可以按它做抗锯齿：
`cov = clamp((hw − dist) / fp + 0.5, 0, 1)`，把线宽 `hw` 加上 `0.5·fp` 可以保证远处的线不断开。

## 正交（纵向压扁）vs 透视：什么时候压扁就够

`ctx.setTransform(S, 0, 0, S·sin(e), …)` 是 `distance → ∞` 时的极限情形。它的代价是平行线不会收拢，远边和近边一样宽。眼睛正是靠线条收拢来判断一个平面是斜放的，
没有收拢，**斜放的正方形看上去就是一个长方形**；另外，压扁方向上的线宽也会一起变细。以下两种情况值得付这个代价：

1. **刻意采用平面风格**（图解、等轴测、信息图）：正交投影保留了沿每个轴的比例，可以直接测量。在 critique 块里写上 `"ortho_ok": "<理由>"`，压扁扫描就不再提示。
2. **两者差别小于一个像素**：`orthoDeviation(cam, 角点)` 返回透视与压扁之间的最大像素差。下表是 19 道棋盘（18×18 格、S=49px/格、distance=30 格）的实测：

   | 俯角 | 远边与近边的宽度比 `edgeRatio` | 透视与压扁的最大差 |
   |---|---|---|
   | 90° | 1.000 | 0 px |
   | 85° | 0.949 | 16.7 px |
   | 60° | 0.739 | 103 px |
   | 35° | 0.606 | 166 px |
   | 35°，distance=200 | 0.929 | 19.5 px |

   「俯角接近 90° 就差不多」只在很窄的范围内成立，85° 时已经差了 16px。判断依据应当是算出来的数，而不是对角度的感觉。

## 手法：提前跟拍、甩镜先定落点

相机参数每帧按 t 计算，所以相机怎么跟拍完全取决于曲线怎么写。下面是两种可选写法：

- **提前约 0.1s、用 `EASE.sine.inOut` 跟拍**：`look` 取主体在 `t + 0.1` 时的位置，画面先一步让出空间，主体看起来是「走进」取景框的。
  代价是主体急停或急转时相机会先动，像是能预知主体的动作；拍机械运动，或者想要「被追着拍」的紧张感时，零提前或滞后更合适。主体运动越快，观众能察觉到的提前量就越小。
- **甩镜前先把落点设为关键帧**：把落点的 `look` / `screen` 对齐到锚点，再从起点插值到它。这样落点就是一个可复现、可核对的值（shotlist 里可以写断言），
  中间的拖影无论怎么画都不会让终点偏移。代价是多了一个需要维护的关键帧；手持感或漫游式的镜头本来就不需要确定的落点。

## 压扁扫描（`scripts/tiltcheck.mjs`，逻辑在 `scripts/lib/tiltscan.mjs`）

这项检查**不能做成会判失败的门**，原因是结构性的：斜放正方形的正交投影和正俯视长方形的投影**逐像素相同**，一个东西本来是不是方的只有作者知道；而且非等比变换也有大量正当用途（挤压拉伸、等轴测、压窄的字、拉伸贴图）。

它能做的是指出可疑的时段：在 seek 期间拦截 2D 绘制调用（路径、矩形、文字、`drawImage`、`fill/stroke(Path2D)`），按**变换矩阵**分组记录屏幕上的外包框；
如果某组的外包框不小于画布的 10%，且奇异值比 σ2/σ1 < 0.9（压扁超过 10%），就提示出来。真正的透视画法不可能用一个仿射变换画出一整块平面，所以透视片在这里的结果自然是空的；一群各自挤压的小球各有各的矩阵，每组都很小，也不会被提示。这两个阈值决定的是检测灵敏度，与审美无关。

**盲区**：在着色器里做的压扁、加载时预先渲染进离屏 canvas 的压扁（只拦截 seek 期间的绘制）、`ellipse()` 的 rx≠ry（透视下圆本来就投影成椭圆，不算在内）、用 CSS transform 压扁的 DOM。
**它检测的是**「有一大块内容是在非等比仿射变换下画出来的」，而不是「这支片子没有透视」：真透视片里如果另有一大块刻意压扁的图解层，照样会被提示；把压扁做在着色器里的片子照样能通过。所以它属于 LOOK 级别。
