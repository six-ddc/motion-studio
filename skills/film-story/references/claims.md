# 断言验的是意图还是画面：`curves.source`

本文展开 SKILL.md 第 6 步。字段写法（`pixels` 规格、`anchor` 写法）见 `references/templates.md`；画面实测由 film-critique 的 `check.mjs` 完成，`check_shotlist.py` 只验证意图。

## 判据：改钉点测试

`check_shotlist.py` 验证的是**分镜里钉下的曲线**。场景照着钉点画时，曲线就等于画面；如果承重变量是由仿真、迭代、物理库或数据推出来的，曲线就只是**意图**，和画面脱钩，脚本照样给绿灯（本仓库样例 ghost-jam 全部通过时，画面里有两处断言并不成立）。判断方法是问一句：把这条曲线的钉点值改掉，画面会跟着变吗？

| 结果 | `source` | 谁验画面 |
|---|---|---|
| 会变（场景读取的就是这些钉点，或者用同一组锚点和值写成的公式） | `curve`（默认，不用写） | `check_shotlist.py`，现在就能验 |
| 不会变（值是从别处推出来的） | `scene`、`pixels` 或 `anchor`，`keys` 可以省略（写了就当作意图来验） | film-critique 的 `check.mjs`，在实现之后逐帧验 |

通过了改钉点测试就用默认值：对纯手钉曲线的片子来说，写 probe 只是额外负担，验的还是同一组数。

## 三种来源各验什么

| | `scene` | `pixels` | `anchor` |
|---|---|---|---|
| 值从哪来 | 场景暴露 `window.probe(t)`，返回 `{曲线名: 数}`，和 `seek` 读取同一份状态 | 截帧后按原生分辨率数像素：`count` / `cx` / `cy` / `motion` | 场景画某个东西时登记的屏幕框 `window.anchors(t)`（film-core `runtime/anchors.js`；写法见 `templates.md`） |
| 验的是 | **意图被执行了**：场景算出的状态是对的 | **像素被画出来了**：观众确实看得见 | **画在了哪里**：某个**有名字的东西**在屏幕上的位置 |
| 抓不到 | probe 说"灯亮着"，但绘制代码没画（或画得比阈值暗） | 状态对，但颜色特征不唯一（别的东西也是这个颜色） | 画了但被挡住或颜色不对；登记在了错误的那一笔上 |
| 代价（1920×1080 实测量级） | 几百帧一次取完，可以忽略 | 约 0.23s/帧（截图加数像素） | 只绘制不截图，约 16ms/帧 |
| 适合 | 不是颜色的量（停车数、里程、弧长位置）和连续量 | "某颜色看得见还是看不见""某物在屏幕上往哪走""相机有没有锁死" | "某物往哪走"但它没有独占的颜色；区分同色的两个东西 |
| 经过谁的代码 | 场景自己的代码（probe 如果另算一遍，验的就只是 probe 自己） | 不经过场景代码，是**唯一的独立旁证** | 场景自己的**绘制**代码（登记写在 draw 那一行，不另算） |

## 选择要点

- **成组锚点的 `cx`** 取的是外包框中心，会随成员进出而跳变，只适合用 `rising` / `falling` 比较首尾，不适合要求逐帧单调的断言；逐帧的方向要用像素质心来验。
- **probe 通过不等于画面为真**：状态阈值和绘制阈值可能不同（probe 报告 0 盏灯时，画面上仍可能有饱和的红色像素）。"看得见红灯"要用像素验，"有车在刹车"要用状态验；承重的那一两条断言，两种来源都写最稳妥。
- 常见的问题是：**一道门实际测的量，和它的提示语让人以为它测的量，并不是同一个**。选 source 前先问清楚，这条断言说的是状态，还是可见的画面。
