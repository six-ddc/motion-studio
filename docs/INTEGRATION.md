## 找到的跨 skill bug

### 1. `align.py --verify` 把答案喂给了 ASR —— 最严重（已修）

这是契约 §6 第 4 条保证（事后校验），整条流水线的最后一道闸门。

`align.py` 把整段脚本当 `initial_prompt` 传给 whisper。对照实验（同模型同音频）：

```
initial_prompt=整段脚本:  从这一刻起，你看见的只有乱码。          ← 只剩最后一句
initial_prompt=None:      你再看一条公开的线路。两端交换参数,…    ← 三句都在
```

两层问题：表层是转写坍缩成 51%；**深层是校验工具不能被告知答案**——
把期望文本喂给 ASR 会诱导它"听出"期望结果，系统性低报真实错误。
`--verify` 存在的理由恰恰是发现 TTS 念错，这个做法把它废掉了。

**修完才看清这个 bug 有多深**：film-narration 的测试片之前报的 **100% 也是喂答案喂出来的**。
真实转写里 `seek` 被听成 `Seq`、`ffmpeg` 被听成 `FFAmpick`——
提示把这些信号全盖住了。也就是说这道闸门在修复前**从未真正工作过**，
而它看起来一直是绿的。

修法：`--verify` 只给一句不含内容的文体提示（什么都不给时 Whisper 会输出繁体）；
术语提示改成显式 `--hint-file`，默认关，且会自动剔除在脚本里出现过的词并告警；
按行报、按字算，把"疑似同音"（pypinyin 确认拼音相同）和"外文词"
从硬错误里分出来单列成"要人听"。

demo 片修复后：**按字准确率 100%，漂移中位 -0.014s，exit 0**，
正确把「在→再」列为要人听——同音字任何 ASR 都分不出，这类错误这道闸门本来就查不了。

### 4. `min_text_px` 单一全局值 + 单位不明

可读性下限按文种差一倍多（film-typography 实测，1080 宽原生）：

| | 400 字重 | 换算成 360px 下的有效 px |
|---|---|---|
| 拉丁 | 26px | 8.7 |
| 中文常规字 | 56px | 18.7 |
| 中文密字 | 72px 内无稳定下限 | — |

单一阈值导致两次误报：先是拿中文的 56 去量拉丁底纹（116 条 FAIL），
改成 26 后仍然 FAIL——因为字段比较的是**有效 px**，而 26 是**原生 px**。
字段该标明单位并按文种分档。

### 5. 逐帧变化的文字区域把 LOOK 刷爆（已修）

乱码每 1/6 秒换一次字形，`readability.time` 为每个变体各报一条，91 条淹掉了真正的 FAIL。
现已合并成 `×43 段中文/符号文字（5.60s–9.50s）` 一条带时间区间的报告。

### 8. 契约漏洞：只钉了 JS，没钉浏览器（已修）

ARCHITECTURE §3 声称"拷贝把运行时版本钉在片子上，半年后老片重渲结果不变"。
但像素由 Chromium 光栅化决定，升一次 Playwright 字形抗锯齿就可能变。
现已：`package.json` 的 playwright 钉确切版本、`film.json` 自动记
`renderer: {chromium, playwright, args}`、启动参数固定 `--font-render-hinting=none`。

后来用四个 Chromium 构建量了这个漏洞到底有多大：**视觉上基本为零，哈希上是真的**
（143→156 跨 13 个大版本，最大差 3/255，见"这台机器上关不掉的"一节）。
所以这条修的价值不在画面，在**可复现性和分片缓存**——不钉的话升一次
Playwright 就让全部逐帧哈希失配、缓存作废，而画面看不出任何变化，
于是"为什么重编了一小时"这个问题会完全没有线索。

## 第二支片子：换一个人、换一种风格，暴露的是另一类 bug

上面那些 bug 全来自 `demo-tls`——**而那支片子是我自己做的**。
自己做的片子有个根本局限：**我知道文档里哪些话是真的**，所以我不会照着一句
没人实现过的承诺去做，也就不会撞上它。

于是做了第二支：`films/ghost-jam`（幽灵堵车，16x9 横版，白天路面，22 辆车跟车仿真）。
它由一个**只读 skill、不许改 skill** 的 agent 当"使用者"从 brief 走到成片，
全程记摩擦日志（`films/ghost-jam/docs/friction.md`，36 条）。
它和 `demo-tls` 在每一个维度上都不同：横版 vs 竖版、白天 vs 暗色、
物理仿真 vs 手钉曲线、有真实文献要核 vs 纯抽象主题。

**结果证实了那个担心：这批摩擦和第一支片子暴露的完全不是一类。**

| | `demo-tls`（我做的） | `ghost-jam`（使用者做的） |
|---|---|---|
| 主要形态 | **工具之间互相对不上** | **文档承诺了没人实现的东西** |
| 例子 | 两个 skill 读同一份 `narration.json` 读法不同；一个工具挑中了另一个工具的派生产物；单位不一致 | 分镜能写"旁白前留白 0.6 秒"而下游一环都没接住；编排器写"迭代期一律半分辨率"而渲染器没这个选项；"字体必须随片打包"是硬约束却不在流水线任何一步出现；脚手架生成的命令照抄就报错 |

**第二类比第一类更难发现**：工具互相矛盾时总会有人撞上；
而**一个没人实现的承诺会一直安静地待着，直到有人认真照做**。

这一类里最贵的一条是片头留白：分镜里设 `pads.lead = 0.6`，
`narration.js` 没有偏移参数、`mux.sh` 不加延迟，于是**画面整体比声音晚 0.6 秒，
而 `check_shotlist`、`seamcheck`、`align --verify` 三道门没有一道会报**
（`--verify` 的漂移为什么没抓到，见下一节的通则）。
使用者只能把留白设成 0 绕过去——**一个看起来能用、实际会静默错位的字段，
比没有这个字段更糟。**

修法是定一个单一真相源：`film.json` 的 `narrationOffset` / `narrationTail`，
`narration.js` / `sfx.mjs` / `subs.py` / `mux.sh` / `align.py` / `check_shotlist`
全部从这一处读，别处不许另存一份；而且脚手架**明写成 0 而不是省略**——
省略掉的字段没人知道它存在，F-027（字体打包）就是这么漏掉的。

**还有一条是正面的，值得记**：使用者反复夸了两处——"候选 0 + 三刀"真的把
最自然的那条路（论文里的时空图）杀掉了而且杀得有理有据；
渲染器的改动泄漏报告被用来**反查改动影响范围**（"只改了辉光半径 → 报告 206 帧变了 →
确认没泄漏到 s6 关键段"），这个用法比"省时间"有价值得多。

## 验证门本身的六个盲区（比 bug 更要紧）

**先说贯穿这五条的那条通则，它比任何一条单独的盲区有用：**

> **一道门出问题时，失败方向几乎总是绿灯；而绿灯的来源通常不是"忘了检查"，
> 是"它测的量，和它的提示语让人以为它测的量，不是同一个"。**

六条里没有一条是实现 bug。每一条都是某个量被诚实地测出来了，只是那个量不是读者以为的那个：

| 门 | 它实际测的 | 它的提示语让人以为它测的 |
|---|---|---|
| `align --verify` 漂移 | 成片音轨 vs `narration.json`（两边都是旁白时间） | 音画同步 |
| `align --verify` 准确率 | 字符串是否相同 | 旁白念对了 |
| `check_shotlist` 的 claims | 作者手写的插值曲线自洽 | 旁白说的状态在画面上为真 |
| 可读性 `cjk_bold=null` | 12–72px 扫描范围内没找到阈值 | 这一档没有稳定下限 |
| `seamcheck` 三门 | 同一个 t 是否总得到同一帧 | 这支片子的时间是对的 |
| 「再渲一遍比对」 | 两次渲染是否一致 | 这次渲染是好的 |
| 可读性 `cjk_400 = 18.7` | 字号 × 观看缩放，阈值在 **1080 宽**上测的 | 这支片的字读得清 |
| 锚点门 `occlude` / `inframe` / `claims.anchor` | 场景**说**它把某物画在哪（绘制时登记的框） | 观众看得见那个东西、在那个位置 |
| `tilt.ortho`（压扁扫描） | 有一大块在非等比仿射变换下画 | 这支片子有没有透视 |
| font_source 判定 6（来得晚） | 采样时刻里有没有分片第一次被用到 | 全片没有一帧用回退字体 |
| texcache-check | 缓存版与每次上传版在采样时刻一致 | 缓存键是对的 |

第八条是第 26 条（空间锚点）自带的：门是新的，盲区是结构性的，所以和像素断言并行写，见第 26 条。

第七条是这一轮新抓的，也是前六条里**代价最实的**一条：它让一支已经"修好"的片子带着缺陷通过。
「有效 px」看着是个画幅无关的量（都归一到 360 观看宽），实测不是——同一字体只换画幅：
×3 缩放下 言 400 的下限 18.7 有效px，×4 是 21.5，×5.33 是 21.4（缩得越狠笔画并得越多）。
ghost-jam 是 1920 宽横版，按 18.7 把字幕定在 106px（19.9 有效px），`check.mjs` 绿；
把 `legibility.mjs` 指到它自己的画幅上重测，真实下限 21.4——19.9 正落在被放过的那一段里。
修法见 film-typography/VERIFIED.md 的双列表：按缩放比分列，取两列里更严的那个。

顺带又踩了一次 177 行那个坑：`legibility.mjs` 的扫描范围 `--min/--max` 是**成片 px**，
而下限是**有效 px**。默认 12–72 是在 1080 宽上定的；原样指到 1920 宽的片上，
72 成片px 只有 13.5 有效px，扫描从没碰到阈值，整列主判据返回 null，
打出来却是一张"每档都只有 1 段"的表，像全面崩溃。
**同一个错第三次了**（`cjk_bold` 的 null、开源项目搜索范围、这次），所以这次写进代码而不是写进文档：
默认范围按 `--frame-width` 缩放，且 null 必须分清是"扫到顶还没够"还是"够过但不稳定"。

**还有一条和它成对的推论，这一轮撞到三次：**

> **验证路径必须和被验证路径是同一条。自己重算一遍的断言，验的是它自己。**

三次分别是：时间映射传反的片子上，物理断言全绿（断言自己调了正确的映射）；
`probe` 报 0 盏灯而画面上有 140 个饱和红像素（绘制从亮度 0.01 起就画，probe 要 >0.5 才算）；
以及我自己量"相机是否静止"时，拿了一个**处在运动段里的参照帧**去比，于是静止量成了一直在动。

所以每加一道门，要能回答两个问题：**它会漏掉哪一类违约？它的提示语会不会让人以为它守住了别的东西？**


### 原来的三道门对"加载期非确定性"是假门

加载时用 `Math.random` 生成布局，门 1a、2、3 **全部通过**，
只有新增的门 1b（换全新页面重新加载再求一次）抓到（13-15 万像素不同）。
原来的三道门全在同一个页面里，对这一类违约毫无作用。

### 缓存泄漏只有带回退路径的乱序求值能抓

三种泄漏（检查点存引用不存副本、仿真循环外挂顺序 `seeded()`、时间往回跳不回退），
冷启动直接 seek 和门 1a、1b **三种都抓不到**，只在门 2 失败，
而且其中一种要到第一个检查点之后（t=1.1s）才露馅。

亲手验过一次：

```
$ seamcheck --film _test-physics --entry replay-leak-rng.html
门 1a  同一页面，同一个 t 求两次：     ✓ 通过
门 1b  全新页面重新加载再求一次：      ✓ 通过
门 2   乱序求值：                      ✗ 6/8 个时刻不同（最多 114348 像素）
```

**结论：写缓存之前先写一个有泄漏的版本，确认测试真的会红，再修好。**

### `align.py --verify` 查得出错字，查不出错音（已部分修复）

`demo-tls` 的成片音轨回转写，**按字准确率 100%、漂移中位 -0.014s、exit 0**——
一路绿灯。而这支片子里「密钥」**一直念的是 mì yào，念错了**（共振峰实测，见下文）。

原因是结构性的：ASR 把声音归一成**字**。念错音但字对，这道门必然绿。
它守的是"音画有没有漂、有没有吞字漏字"，不是"字念得对不对"——
这两件事看起来都叫"校验旁白"，实际上一个能自动、一个当时以为不能自动。

**后续更有意思：修好读音之后，这道门反而变红了。** 因为有效的修法是同音字文本转写
（`密钥/密月`），Whisper 老老实实转写成「蜜月」，而 `pypinyin` 把脚本里的「密钥」
注成 mì yào，于是比对判成硬错误，准确率掉到 94.7%、exit 1。
也就是说这道门原来的行为是：**念错了给绿灯，念对了给红灯——方向完全反的。**
现在对词典里写了等长同音字转写的词按词典读音判；反过来，
如果转写成的是和默认读音同音的字（`密钥/秘药`），记为硬错误。

**仍然有盲区**：Whisper 照写原词「密钥」时，校验器分不出念的是哪个音。
所以共振峰复核省不掉，这道门只能缩小盲区，不能消掉它。

### 分镜断言验的是作者的意图，不是画面（已修）

`film-storyboard` 的 `claims` 机制声称守的是"旁白说的状态必须在画面上为真"。
但它验的是**作者手写的插值曲线**——对 `demo-tls` 那种所有状态都来自手钉曲线的片子，
意图和画面是同一件事；对任何物理或涌现驱动的片子，两者完全脱钩。

`films/ghost-jam`（22 辆车跟车仿真）上实测：`check_shotlist` 全绿，
而真实仿真里 s4 旁白正说"一辆传一辆"时画面开头 **0.60 秒一盏灯都没有**，
s3 末尾全部熄灭 0.07 秒。

现在 `curves.<名>.source` 可以写 `scene`（场景暴露 `window.probe(t)`，由 `check.mjs`
逐帧取真实状态）或 `pixels`（截帧统计）。判断要不要写 probe 的判据叫**改钉点测试**：
把这条曲线在 shotlist 里的钉点值改掉，画面跟着变就是手钉曲线，不用写 probe；不变才要。

**代价和直觉相反**：担心的逐帧 `evaluate` 其实极便宜（708 帧一次取完 0.02 秒），
贵的是像素（截图 187 ms/帧）。所以 probe 常规、pixels 按需。

**这条还暴露了交叉验证的边界。** 那支片子的作者自写了一个 `simcheck`，
它和 `check_shotlist` 都放过了 s4 那段——因为**两者共用同一条断言**（写的是 `rising`，
只比首尾两个端点 0→5，中间平不平不看）。
本轮交叉验证奏效的几次（两份中文数字解析互比、两个独立测量撞车）都是**独立实现**；
**共用判据时，交叉验证提供不了任何额外信息。**

### 确定性全绿，而片子在错误的时刻播放正确的帧（已修）

叙事片经常要"时间加速"：旁白说"没过几分钟"，画面只有 3 秒。于是影片时间 t
和仿真时间之间有一个映射。**把这个映射传反、或者忘了传**，会得到一支
完全确定、可乱序求值、循环接缝完好的片子——`seamcheck` 三门全绿、
`physcheck` 的 B/C/D 全绿——**它只是在错误的时刻播放正确的帧**。

确定性闸门结构上抓不到这一类：它们验的是"同一个 t 是否总得到同一帧"，
而这里每个 t 都稳定地对应了错的帧。现在 `physcheck` 新增 E 组专门查它。

实测反例 `warp-inverted`：**只有 E4 红，seamcheck 绿**。
而且在那个写错的版本上，物理断言三条**全绿**——因为断言自己调了正确的映射。
这就是上面那条推论的来源。

### 一次渲染可以静默地坏掉，而所有门都过（已修：门 5）

**新装或新拷贝的浏览器二进制，第一次启动会出纯白帧。**
新拷一份目录再启动，6/6 次复现；之后的启动 0/158。
拿它渲整片：`render.mjs` 报 ✓，而成片里 **84/326 帧是纯白的**，一声不吭。

**这一类的检出办法和直觉相反。** 最自然的想法是"再渲几遍互相比"——
实测它**没有任何检出力**：门 1a/1b/2 全过，两遍之间也完全一致，
因为它们坏得一模一样。有检出力的是**和那次渲染留下的逐帧清单对账**，
它报了 ✗ 88/326 帧。

所以 `seamcheck --relaunch N`（门 5）不是"重复跑"，是"重复跑 + 对账"。
对账条件不满足时（设置不同、浏览器构建不同）它会明说"不对账"，不假装通过。

但"明说不对账"还不够——**说的得是作者能据此行动的那句话**。
原来帧数不同也归进笼统的"设置不同"，作者第一反应是自己 `--sub` 传错了；
实际上帧数变了十有八九不是设置问题，是旁白重录后 `film.json` 的时长回写了，
`out/` 里那条成片按旧时间轴渲的、**已经过期**。现在这一种单独报
"时长变了（那次 75 帧 / 2.500s → 现在 60 帧 / 2.000s，差 -0.500s）"并点出重渲；
其余情况也只列出真正不同的键（`sub: 1 → 4`）而不是整个 JSON。
闸门的输出是给人读的，归类太粗等于把信息藏起来。

顺带：**缩小分辨率会损失检出力**。合成测试里 0.5x 漏掉 1×1 / 2×2 像素块、
幅度 ≤3/255 的差异，4×4 以上全部抓到。所以 0.5x 抓不到"145 那一条扫描线"那一类，
但抓得到纯白帧和跨启动差异。

**这类盲区的共性**：三个盲区都不是实现 bug，而是**门测的量和你以为它测的量不是同一个**。
加载期非确定性（门在同一个页面里测，而问题在跨页面）、
缓存泄漏（门顺序求值，而问题在回跳）、
读音（门比字符，而问题在音素）。
所以每加一道门，都要能回答一句：**它会漏掉哪一类违约？**

## 开源项目比对

完整报告见 [`oss-borrowings.md`](oss-borrowings.md)（读了 Remotion / Motion Canvas / Revideo / Manim 源码）。

落地的（实测数字）：

| 借鉴 | 效果 |
|---|---|
| CDP 截图替代 `locator.screenshot` | 单页 1.99×，输出逐像素一致 |
| 并行渲帧 + 分片编码 | 16 worker / 8 浏览器 **8.3×**；6 种拓扑下帧哈希与串行逐帧相同 |
| 每帧 `await document.fonts.ready` | 1 行 |
| 钉渲染器版本 + `--font-render-hinting=none` | 见上 |
| 逐帧哈希清单 | 能报"改了 1.5s 之后，实际 14 帧变了 → 1.53–2.00s" |
| `seamcheck --parallel`（门 4） | 1 页顺序 vs N 页并发，逐帧比 md5 |

~~**Remotion 没有乱序求值的像素门**~~ **这条第一轮写错了，第二轮更正。**
它**有**：`packages/it-tests/src/rendering/gsap-render-parity.test.ts` 里就有串行、
并发、乱序 `renderStill`、重复渲染的逐帧 pixelmatch 比对。
第一轮只搜了 `renderer/` 和 `core/` 两个目录就下了结论——**搜索范围不等于不存在**，
和「`cjk_bold` 的 null 其实是扫描范围截断」是同一个错。

更正之后的差别仍然在，只是性质不同：**它只测 Remotion 自己的 GSAP 适配层，
用户拿不到这道门。** 面向用户的那一侧仍然是 ESLint 警告 `Math.random`、
文档承认闪烁是常见 bug、兜底 `--concurrency=1`。
我们把它做成了**每支片子的验收门**，这一条算我们做得更好——
但要老实说清楚：Remotion 自己也需要这道门，也写了，只是没交给用户。

**而且它那道门比我们的宽。** 实测（用本仓库 node_modules 里的 Playwright 1.64.1）：
pixelmatch 即使设 `threshold: 0` 也不等于逐像素相等，它仍会把判定为抗锯齿的像素剔掉；
拿 Chromium 自身非确定性的一组样本测，8 个差 1/255 的像素**全被剔掉**。
Playwright 默认阈值 0.2 更宽，会放过「整幅画面亮度偏 8/255」这种全局偏移。

**对我们的反向提醒**：Chromium 同机同构建也存在 ±1 的非确定性。
我们的门容差为 0，默认路径实测 10/10 一致还没撞上，但这是潜在的误报来源。
撞上时该调的是"容差从 0 放到 1"，不是关掉这道门——而且要先确认放宽之后
它还抓得住真问题（见 Manim 的做法）。

已经比它好的：`spring({duration, overshoot})` 是闭式反解（Remotion 的
`measureSpring` 是逐帧扫描的启发式，不能按过冲反解、没有过阻尼分支）；
运行时禁用 API 探针能抓到第三方库内部的调用，ESLint 抓不到。

### 第二轮比对：开源项目怎么验"渲出来的确实是想要的"

第一轮只比了**渲染性能**那一侧。这一轮这套东西暴露的是**验证**那一侧，
于是带着具体问题又读了一遍源码（Manim / Remotion / Motion Canvas / Revideo，
加上前端视觉回归生态：Playwright、pixelmatch、jest-image-snapshot、reg-suit、BackstopJS）。
完整报告和每条的借鉴/不借鉴决定见 [`oss-borrowings.md`](oss-borrowings.md) §5。

**结论一：内容断言是一块真空白，但很窄。**
所有项目都只做两件事——和**人批准过的基准**比（视觉回归），
或者用**答案能独立算出来的人造场景**测框架自己。
**没有一个项目对用户自己的作品做"对照规格"的内容断言。**
这既不是我们想多了，也不值得往通用能力上扩：我们每支片都是新的（没有基准）、
没有人逐帧看、而旁白本身就给出了可机检的命题——这三个前提同时成立的场合不多。
所以决定是**保留现有的 claims + probe，不扩展成通用的内容断言框架**。

**结论二：Manim 独立走到了我们这一轮踩出来的两条结论上。**

| Manim 的做法 | 对应我们的哪条 |
|---|---|
| 基准存**解码后的 uint8 数组**（`.npz`），不是 PNG | 我们比 PNG 字节错过一次，解码后才发现 0 像素不同 |
| 229 个图形测试里约 **70% 只比最后一帧**；多帧的用 427×240、6 fps | 和我们两个盲区同构：「时间映射错了但终态是对的」「降分辨率漏掉小差异」 |
| 容差：每通道差 ≤1，超出的像素占比 <1e-5 才警告放行 | 我们容差为 0。Chromium 同机同构建有 ±1 非确定性，这是潜在误报来源 |
| 三个操作系统共用同一份基准，Linux/macOS 的 Cairo 从源码编固定 1.18.0 | 和"钉渲染器版本 + 字体随片打包"是同一个主意 |
| 生成基准前**要求人先看一遍**（`--set_test`） | 和"主观项必须人看、模型只写描述"一致 |

两条独立得出同一结论，比任何一方自己论证都有说服力。

**结论三：时间重映射这一类，没有项目在检测。**
Remotion 靠 API 形状防（组件里拿不到绝对帧），Manim 和 AE 不检测。
我们的 E4 是目前唯一一道，但它守的是"声明的映射 == 实际用的映射"——
**声明本身写错了照样绿**，这个边界要写明，别当成已经关掉。

## 没被任何片子走过的代码路径

上面的 11 个 bug 都是**跑真片子**暴露的。还有一类更隐蔽：
**跑了片子也暴露不出来，因为没有一支片子走到那条路径。**

### 14. 换一个 Chromium 构建，所有片子都加载即失败（已修）

Chromium 143 / 145 / 151 加载页面时都会请求 `/favicon.ico`，dev server 返回 404，
而 `scene.mjs` 把任何 404 当成场景错误中止。**这三个版本下所有片子都渲不出来。**
默认用的 156 不请求 favicon，所以这个 bug 在默认路径上永远不会出现——
它只在"换构建"这件事第一次被做的时候才暴露。现在只滤掉这一条，
场景自己缺资源的 404 照常中止。

### 16. 各 skill 的检查脚本用和渲染器不同的浏览器条件

`physcheck`、film-typography / film-webfx / film-assets 的检查脚本都自己
`chromium.launch()`，**不跟随 `FILM_CHROMIUM`，也不带 `--font-render-hinting=none`**。
也就是说，这些 skill 验证自己的运行时所用的浏览器条件，
和真正渲片子时的条件不是同一套。目前这不影响结论（同机同默认构建），
但它是一个结构性隐患：**一个 skill 在 A 条件下验过，片子在 B 条件下渲。**
统一的做法是都走 `film-motion` 的 `launchBrowser()`。未修，记在这里。

### 17. 片头留白在下游没有任何一环接住（已修）

分镜能写 `pads.lead = 0.6`，`narration.js` 没有偏移参数、`mux.sh` 不加延迟，
**画面整体比声音晚 0.6 秒而三道门都不报**。见上一节。
修法：`film.json` 的 `narrationOffset` / `narrationTail` 作为单一真相源，
六个工具全部从这一处读；改完之前旧字段与新字段不一致会报错（退出码 4）。
端到端验过：`_test-narration` 设 0.6s，`--verify` 100%、漂移中位 -0.024s，
从无声成片逐帧量四个弹簧点，都在期望时刻后 36–58 ms（一帧 33 ms）。

### 20. 事实对账的量词表写死了上一支片子的单位（已修）

量词表是照交子/唐片调出来的，不认"辆/米/公里/分钟"。按文档的自然写法
`22辆` 直接 FAIL，只能写裸数字绕过——**而绕过意味着单位不在对账范围内，
等于悄悄缩小了这道门的覆盖面**。
换了机制而不是补表：匹配词按"数值 + 单位"解析，单位由片子自己声明，不查白名单。
顺带查出旧逻辑还有**静默漏报**：旁白写"五分钟"，"分"不在表里，整个数被跳过，`exit 0`。

### 21. 中文口语省略末位单位解析错，会放过错数（已修）

`三百五` → 305（应 350）、`一万二` → 10002（应 12000）。
端到端后果：旁白"三百五米"对 facts 里的 `305米`，**旧版 `exit 0`，一个错数被放过去**。
这个 bug 是 `film-narration` 抽取 `film-research` 的源码做**交叉校验**发现的，
25 个输入里揪出 4 个分歧——**不是靠任何一方自己加测试用例**。
该交叉校验现在是常设的（`align.py --selftest`，33/33 一致）。

### 22. 成片校验不做数字归一，含数字的旁白几乎必然误判（已修）

Whisper 把"二十二"写成 `22`，逐字比对记 3 个硬错误。ghost-jam 因此 95.6% FAIL。
归一后 98.9% PASS，转写本身没变。
另一个方向的毛病更隐蔽：`22→32` 旧版判 **0 个硬错误**——两边都是纯 ASCII，
被当成外文词拼写差异放过了。
实现时守住了一条：解析不了的串退回逐字比，**不剔出分母**——剔掉会让准确率虚高，
那是和误报相反方向的假绿灯。

### 23. 可读性阈值表默认"有效 px 与画幅无关"，对横版片是假绿灯（已修）

见上面盲点表第七条。`check.mjs` 的 `cjk_400 = 18.7` 是在 1080 宽→360（×3）上测的，
拿去判 1920 宽（×5.33）的片子放过了 18.7–21.4 这一段。ghost-jam 的字幕 19.9 落在里面，
**第 6 轮据此把一个 FAIL 关掉了，缺陷其实还在**。
现在阈值表按缩放比分列、取两列里更严的那个；只修中文不修拉丁，
因为拉丁的 mmm 统计量在 ×5.33 下给出"字重越粗下限越低"的反物理结果，噪声太大不能当判据。
配套：`legibility.mjs` 的默认扫描范围改成跟着 `--frame-width` 缩放，
且 null 必须分清"扫到顶还没够"和"够过但不稳定"。

### 24. `mux.sh` 推荐的 `--limit auto` 会让念读核验直接红（已标注）

峰值超标时 `mux.sh` 提示"降低 --lufs，或加 --limit auto"。照做之后峰值确实好看了，
**人声也被压坏了**。ghost-jam 实测，两组各复现两次（同一段音频 Whisper 是确定的）：

| 混音 | 归一模式 | True peak | `align --verify` |
|---|---|---|---|
| `--lufs -14 --lra 16` | dynamic | −1.0 dBTP | **98.9%** ✓ |
| 同上 `+ --limit auto` | linear | −1.4 dBTP | **96.7%** ✗（阈值 97%） |

用 2.2 个百分点的念读准确率换 0.4 dB 的峰值余量。多出来的错是 `事故→试过`、漏「的」。
而 −1.0 dBTP 本来就满足常见发布规范（YouTube/Spotify 的天花板就是 −1.0），
−1.5 只是本套件更紧的内部目标——**为了一个内部目标去损伤影片真正的承载物**。

这条的形状和别的不一样，值得单独记：**不是闸门漏报，是一个工具的建议把另一个闸门推红**。
两道门都正常工作、都说了实话，坏的是它们之间没有人提醒"这两件事会打架"。
所以修法不是改任一道门，而是在**提示语出现的那一行**把代价写出来：
现在那条提示后面直接跟一句"加了就重跑 `--verify`"。

### 25. 一处音画错位穿过了三层断言，每层漏法不同（已修）

ghost-jam 7.5s：旁白"一辆车轻轻慢了一下"是单数，画面上已经两辆车亮灯（后车只晚 0.43s）。三层断言全绿：

| 层 | 写的是 | 漏在哪 |
|---|---|---|
| 分镜断言 | `灯数 >= 1` | **比旁白弱**。旁白说"一辆"，该验 `== 1` |
| 分镜意图曲线 | `s3@慢=1 → s4.start=2` 线性插值 | **意图本身写错**：插值等于说"s3 里灯数在涨" |
| 片内 `simcheck` | 扰动后 **0.3s** 内灯数 ≤ 1 | **窗口恰好比缺陷短**：后车是 0.43s 亮的 |

第三种最阴：它不是写错了，是写得"刚好够过"。窗口一旦不是从旁白的时间结构里来
（"一辆"这句话从哪到哪），而是作者拍了个数，它就会被调到恰好能绿的长度。
**断言的强度和窗口都要从旁白抄，不要从画面现状抄**——从画面抄，验的就是画面自己。

根因在物理：OVM 没有反应时间，后车即时响应；扰动 2.0 m/s² 是一脚实刹不是"轻轻"。
改成 0.9×2.4s（轻而长）。只调轻不行——同一个旋钮还管着"s4 不许黑场"，扫 20 组只有一档两头都满足。
三层都加强后各自做了阴性对照（换回旧参数，三层各自报红）。

### 26. 套件暴露了时间和状态，没有暴露空间：两处构图缺陷没有任何门能查（已修：空间锚点）

**这件事是什么。** 层与层之间本来就要交换数据：动画层知道"某个东西此刻画在屏幕哪里"，字幕、特效、评审、分镜断言都要用这个位置。
套件原来只暴露了**时间**（`vo.at`、`window.MARKS`）和**状态**（`window.probe(t)`），没有**空间**。于是：
字幕底条会不会盖住参照树只能裁原分辨率帧人眼看；"黄车往左、灯团往右"只能按颜色范围数像素间接测；
"旁白主语在画面里"根本没有门。现在场景在**绘制路径上**登记锚点（film-motion `runtime/anchors.js`，`window.anchors(t)`），
契约、形状取舍（独立通道而不是 probe 的保留键）见 ARCHITECTURE §10；消费者是 check.mjs 的遮挡门 / 出画门（`occlude` / `inframe` 法律）
和 shotlist 的 `source: "anchor"`。只暴露数据，不做布局——谁不许挡谁、安全区多宽，写在每支片自己的 critique 块里。

**撞到了什么。** ghost-jam（第 7 轮八门全绿）一接上就两道门各红一处，**两处都是真缺陷**：

| 门 | 发现 | 为什么原来查不到 |
|---|---|---|
| 遮挡门 | s6 里字幕底条盖住**参照树**树干 9.5px（192/282 帧） | 第 7 轮字幕 106→119px，人工复查记成"盖住中景小树的树干"，没认出那就是 style_guide 要求"完整露在字幕带上方"的参照树 |
| 出画门 | "有车被逼停了"时停住的车被左边缘切掉 57px、只剩 60.3% 在画面内；灯团切掉 104px | 承重 MARK 只查"够长、画了、对上词"，不查"画在了画面里" |

修法是改推近终点（`CAM_CLOSE` z 2.0→1.85、x 0→−3、y 31.5→32.5），重渲后八门 + 两道新门全绿。

**像素版与锚点版是否一致。** 并行跑（s6、同 286 帧）：**结论一致**。黄车 r=1.000、恒差 7px。
灯团端点位移一致（+0.428 / +0.417），但**逐帧方向只有 179/285 同向**、差中位 69px——成组锚点是外包框，成员进出团时框边跳变，
还算进了出画的车；像素质心按看得见的红像素加权。所以成组锚点的中心只能用于比端点的断言。

**顺带撞到的三件：**
1. **第一版法律门没查纯函数，阴性对照拆穿了它。** 把上一帧的框并进本帧，`claims.anchor` 有顺序/倒序比对，两道法律门却照常 PASS——
   它们按时间顺序读表，读到的是"上一帧的位置"而不自知。现在每条法律也顺序/倒序各取一遍。
2. **累积型泄漏会饱和，顺序/倒序比对抓不到。** 把历史框不断并进来，几帧后两种顺序得到同一个大框：两道法律门照常 PASS，
   只有 `claims.anchor`（cx 不动了）报红。和 probe.pure 是同一个结构盲区；要抓得做全新页面冷求值（门 1b 那样），没做。
3. **"没声明就不生效"是验过的，不是推出来的。** demo-tls 用改前/改后 check.mjs 各跑一遍，findings / timeline 逐项相同；
   check_shotlist 对没用 anchor 的片子 `--plan` 与正常输出逐字节相同（为此把一句提示语改成了按需拼接——原来它对所有片子都多出"/anchor"）。

**它测的量 vs 提示语让人以为它测的量**（接盲区表那一列）：锚点门测的是"场景说它画在哪"，不是"观众看得见什么"。
被盖住、alpha 为 0、登记在错的那一笔上，锚点门都绿。所以承重的方向断言像素版和锚点版**并行**写，不互相替代。

### 27. 套件管了机制的发散，没管讲法和长相；片子之间互不知道（已补：讲法 / 视觉方向 / 近作对照）

**这件事是什么。** film-storyboard 第 2 步让**机制**发散（候选 0 = 默认画法，不同类的候选，三刀砍），这一步是好的。
但一支片子还有两个会自动退回默认的决定，套件一步都没管：
① **讲法**——脚本按什么结构讲。film-narration §三只管 script.json 的格式，没有一步问顺序，于是默认写成百科顺序（定义 → 历史 → 规则 → 总结）；
② **长相**——调子、材质、镜头、字、色。style_guide 直接写一份，写出来的是最顺手的那种；
③ **片子之间互不知道**。没有一步让新片看一眼仓库里已有的片子。模型不记得上一支长什么样，"别和上一支一样"靠自觉做不到。

**为什么之前缺。** 套件是从"两支片子都画了网格"那次失败长出来的，所以全部力气花在机制上；而机制对了、长相和讲法仍然是默认值的片子，
在验收表上一路全绿。证据：ghost-jam、demo-tls 都没有任何视觉方向的取舍记录，docs/ 里没有一处提到别的片子。
唯一做了的是 weiqi-intro（"视觉概念：三个方向，选了一个""和前两支片子拉开的距离"）——是编排方在任务说明里手动要求的，套件本身没要求。
用户对它的评价是"还行"。另一个用户原话指向同一处："Claude Design 的思想很重要，它避免了千篇一律的设计风格"。

**怎么补。** 方法吸收自 Anthropic 的 frontend-design / canvas-design 两个 skill 的 Design Thinking，不硬依赖它们
（借了什么、改了什么见 [`oss-borrowings.md`](oss-borrowings.md) 第 6 节）。三样东西：

| | 落在哪 | 判据 / 实质 |
|---|---|---|
| 讲法的发散 | mechanism.md「讲法」一节，机制之后、旁白草稿之前 | 候选 0 = 本题默认讲法；其余结构分属不同类（类表查重用）；两刀：承重那一刻是不是高潮、观众能复述哪一句 |
| 视觉方向的发散 | style_guide.md 顶部，排分镜之前 | 候选 0 = 默认长相（最省事的 + 上一支片子的）；每个候选写名字、宣言、核心手法、最难忘的那一个东西、输在哪 |
| 近作对照 | `film-storyboard/scripts/siblings.mjs` + style_guide「近作对照」 | 点名可能撞脸的片子，写拉开了什么或有意重复了什么；重复可以，不知不觉的重复是要抓的 |

方法文档 `film-storyboard/references/divergence.md`；门在 `check_shotlist.py`（已被本文件的 accept.mjs 当 shotlist 门调用），
**宽容格式、严格实质**：候选可以是 `###` 标题、粗体行、列表项，编号 0/A/一 都认；实质是 ≥2 个候选、标了选定、落选的写了输在哪，
或者带理由的跳过声明 + 一行选定；近作对照要点名一支真实存在的片子。`--plan` / `--verdict` 输出不变（发散检查放在它们之后）。

**样板一字不改就过，阴性对照全红。** weiqi-intro 的 style_guide 原样：视觉方向 OK（3 个候选、选定 A）、近作对照 OK（点名 demo-tls、ghost-jam）。
在 scratch 副本上（`FILMS_DIR` 指过去）逐项改坏：删整节 → 视觉方向和近作对照各报一条失败；去掉"选定"、删掉落选的"输在哪"、只留一个候选、
近作对照把片名换掉、讲法节是没填的模板、讲法缺候选 0、跳过声明只剩"跳过"两个字、跳过了但没写选定——九种改法**每种都 exit 1**，
还原后 exit 0；讲法补上候选 0 后 exit 0。系列片写法（"沿用自 weiqi-intro" + 近作对照里声明有意重复）exit 0。

**ghost-jam / demo-tls 如实补记**，不编造当年没想过的候选：style_guide 写"跳过发散：事后补记：本片定稿时套件尚无此步骤，当时未做视觉方向发散"，
把下文「视觉」里已写明的实际选择摘成"选定"；近作对照、讲法（在 mechanism.md）同样补记。补完 accept --quick 两支都全绿。
`_test-storyboard` 的三个对账夹具补了一份"夹具，不是片子"的跳过声明，四个用例的退出码仍是 1 / 0 / 2 / 1。

**eval-clearing / eval-deepsea 如实报红。** 它们是被手动停掉的未完成评测片（旁白合成了，scene.html 还是脚手架桩），
本来就没做过设计。给它们补"事后补记"会把一支从没做过设计的片子写成"做过、只是跳过了发散"，那是假记录，所以不补。

**为什么讲法"整节都没有"暂时只警告。** 这一步刚出现，仓库里还没有一支片子做过讲法发散——包括样板 weiqi-intro：
它的讲法（历史 s1–s3 → 气的规则 s4–s10 → 两只眼 s11–s12）正是候选 0 的形状，而且大半是 brief 给的，但没有一步记下这一点。
直接判失败会让唯一的正面样板在修片中途变红。所以：新片从 `assets/mechanism.md` 拷到的模板里有这一节，**节在但没填 = 失败**；
整节不见了 = 文档早于这一步 = 警告。等第一支从头按本方法做的片子（计划中的 weiqi-ch1）过了这道门，
把 `check_shotlist.py` `divergence()` 里那一处 `warns` 改成 `errors`，让"整节没有"也失败。

**siblings.mjs 看图后的发现。** 第一次拼图（ghost-jam 视角）就看出两件表上看不出的事：
① 三支未完成片（eval-clearing、eval-deepsea、weiqi-ch1）现渲出来是同一张图——new-film.mjs 的占位球。拿它当代表帧会误导，
现在识别脚手架占位标记，标成"无代表帧"；
② poster 是片头那一帧，不一定是签名：weiqi-intro 的 poster 是历史段的 3/4 俯视空棋盘，它最有辨识度的"气泡透镜"一帧都没有；
唐片的 poster 只是一个"唐"字。所以 siblings.png 对"长相"的代表性取决于 poster 选在哪一刻——没修，记在 film-storyboard VERIFIED.md 的没解决一节。

**它测的量 vs 提示语让人以为它测的量**：门测的是"这一步留下了实质的痕迹"，不是"候选真的不同"或"选得好"。
两个候选只在颜色上不同、写得像两个，门照样绿。那是判断，只能靠 film-critique 打分时人看。

### 28. 字级时间戳挤成一团，下游没有任何一道门看得见（已修：`tts.py` / `--verify` 拿能量包络核对）

weiqi-intro s4：接口把「上、下、左、右」四个字的时间戳挤在 0.1 s 内，声音里是四段相隔约 0.75 s 的能量。
场景按字触发（`A('s4','下')`），画面整串错拍。`tts.py` 只把它们列进了低置信度，作者是自己画包络才发现的。

这条的形状值得记：**唯一的时间真相源错了，所有下游门都是从它派生的，所以全绿。**

| 门 | 为什么抓不到 |
|---|---|
| `align.py --verify` 漂移 | 看**全片中位数**（阈值 0.15 s），四个字淹在 200 多个字里 |
| film-critique `mark.sync` | 画面 MARKS 和 narration.json 出自**同一份**时间戳，必然对上 |
| `tts.py` 低置信度清单 | 只是提示，conf 不低的挤压也有（人为挤压的对照组 conf 0.6–0.9） |

修法：唯一独立的证据是声音本身。`film-narration/scripts/_timing.py` 按停顿标点把每句切成意群，**只用时长**（不用时间戳）
把意群动态规划对齐到 wav 的能量段，比每个意群起点：差 ≥ 0.20 s 判失败。`tts.py` 合成完就查（退出 6，narration.json 照写以便 `--only`），
`align.py --verify` 每次也查（退出 6）——**accept 的 verify 门因此会红**。

- 阈值从实测定：仓库 10 支片 85 句正常旁白最大 0.15 s；挤压实例 ≥ 0.22 s。顿号原句现合 4 次 4/4 挤压；逗号版 2 次 1 次在后面的「它、」处挤。
- 普查顺带抓到 3 处没人发现的真错：**eval-clearing s5**「是」晚 0.25 s；**weiqi-ch1 d6**「一样」晚 0.22 s、**d8**「有两只眼的棋」晚 0.78 s（6 个字挤进 0.31 s）。
  weiqi-ch1 是进行中的片子，**要通知它的作者**：现在还没有成片所以 verify 门不适用，出了成片 verify 会因这两句退出 6。
- 没解决：判据两边余量都只有约 0.05 s；只验过 volcano-stream（edge 引擎见下条）；意群内部的挤压（不在停顿后）只做警告（字尾截短 / 字在静音里）。

**顺带发现（未修）**：edge-tts 7.x 的 `Communicate` 默认 `boundary='SentenceBoundary'`，`tts.py` 的 edge 引擎从此**拿不到词边界**，
每句都静默退回 Whisper 反推（narration.json 里 `src: whisper`）。SKILL.md 说 edge「原生返回词边界」已不成立。修法是传 `boundary='WordBoundary'`，没改，等确认。

### 31. 成片真峰超标没人标红（已修：`mux.sh` 与 `--verify` 各一道门）

loudnorm 退回动态模式后，限幅器按 -1.5 压，**AAC 编码再过冲**：weiqi-intro `--lufs -14` 成片 **-0.51 dBTP**，
连 YouTube / Spotify 的 -1.0 天花板都超了，`mux.sh` 只打印了数字。

修法：量交付的 mp4（loudnorm 测量，两位小数——ebur128 只打一位，ghost-jam 的 -1.01 显示成 -1.0）。
**> -1.0 dBTP 失败**（`mux.sh` 退出 5、文件照写；`--verify` 退出 5），-1.5 到 -1.0 警告。门放在 film-narration 自己的两个工具上，
accept 的 verify 门（`align.py --verify`）因此覆盖所有**有旁白**的成片。

| 片子 | 成片 TP | 判定 | 处理 |
|---|---|---|---|
| weiqi-intro | -0.51 → **-1.44**（`--lufs -14 → -16`，不加 `--limit`） | ✗ → ⚠ | 重混；`--verify` 99.1% → 100.0% |
| ghost-jam | -1.01 | ⚠（离天花板 0.01 dB） | 不动，记进 review_log |
| demo-tls | -1.43 | ⚠ | 不动 |

动态模式下真峰随 `--lufs` **不单调**（weiqi-intro 扫 -15…-19：-1.35 / -1.13 / -1.44 / -1.10 / -1.49 / -1.51），过冲 0–0.4 dB；
要稳定 ≤ -1.5 只有线性（`mux.sh` 现在会算出保持线性的 `--lufs` 上限）。两种表对同一文件最多差 0.2 dB（-17 那版 -1.10 vs -1.3）。

**（已协调，见第 37 条）** 原需求：verify 门的前置条件是 `narration.json` 存在。**没有旁白、只有配乐/音效的成片**
（音乐主导的片子）不会进 verify 门，它的真峰没有任何门查。建议 `check.mjs --mp4` 在量流时长、音画差的同一处加一项 true peak：
`ffmpeg -i <mp4> -af loudnorm=print_format=json -f null -` 取 `input_tp`，**> -1.0 失败，> -1.5 警告**，与 film-narration 同阈值同测量
（或者直接只在没有 narration.json 时查，避免两道门对同一文件重复报）。

> **补（第 28 条「顺带发现」已修）**：`tts.py` 的 edge 引擎改为按签名显式传 `boundary='WordBoundary'`（老版本 edge-tts 没有这个参数就不传），
> 现合验证拿到原生词边界、不再退回 Whisper；edge 的 token 不带标点，`_timing.py` 改从台词原文取停顿标点切意群，
> volcano 86 句的结果逐项不变，edge 原生时间戳按 volcano 同等判（只有 `src: whisper` 的反推仍只警告）。见 film-narration VERIFIED.md 第 25 节。

### 32. 套件只有二维相机：斜着看一个平面，最省事的写法是错的，而且没有门能查（已补：透视相机；门只能做成疑点）

**撞到了什么。** weiqi-intro 第一版的开场棋盘"像长方形"——用户看成片一眼看出，所有门全绿。
`film-motion` 的 `camera()` / `applyCamera()` 只做平移缩放，canvas 2D 只有仿射变换，于是"斜着看"最省事的写法就是
`setTransform(S, 0, 0, S·sin俯角, …)` 纵向压扁。那是**正交投影**：平行线不收拢、远近边一样宽，斜放的正方形在画面上就是长方形。
作者后来自己写对了（针孔投影 + 着色器里精确反投影，棋盘/厚度/影子/棋子/气泡共用一个投影），但这套东西只活在那一支片子里。

**修法。** 提炼成 film-motion 的随片运行时 `assets/runtime/camera3d.js`（基础集，新片自动拷；老片不受影响）：
`camera3d({S, elevation, distance, look, screen, yaw})` → `project(x,y,z)` / `unproject(X,Y,h)` / `uniforms()`，
加一段 `CAMERA3D_GLSL`（`cam_unproject` / `cam_project` / `cam_footprint`）。实测与 weiqi-intro 的 `project()` 逐点差 2.3e-13 px；
GLSL 反投影与 JS 投影互逆 ≤ 5.5e-4 px；正俯视时 z=0 平面透视量精确为 0。
文档把"压扁 = 正交"写成代价与判据：`orthoDeviation(cam, 角点)` 给出透视与压扁的像素差——19 道棋盘在 85° 俯角已差 16.7px，
"接近正俯视就差不多"只在很窄的范围成立。

**门为什么只能是疑点。** 斜放正方形的正交像，与正俯视一个长方形的像**逐像素相同**；"它本来是不是方的"只有作者知道。
而非等比变换另有大量正当用途（挤压拉伸、等轴测、图解）。所以 `film-motion/scripts/tiltcheck.mjs`（逻辑 `scripts/lib/tiltscan.mjs`，
check.mjs 接成 `LOOK tilt.ortho`）只做能做到的那件事：seek 期间按变换矩阵分组记屏幕外包，某组 ≥ 画布 10% 且奇异值比 < 0.9 就指出时段。
透视画法下一整块平面不可能用一个仿射变换画出来，所以真透视的片子在这里自然是空的。有意正交的片子在 critique 块写 `"ortho_ok": "<理由>"`。
阴性对照：压扁 / Path2D 压扁 / 方贴图拉扁三种错法都报，camera3d 透视、正俯视、12 个挤压拉伸小球（最大组 0.7%）都不报。

**接上就撞到一支真阳性：ghost-jam。** 整片 100% 面积 σ2/σ1 0.52（`TILT = 0.52` 压扁整块地面）。它的 style_guide 写"近大远小只做简单透视"，
场景的 `proj()` 却是纯正交（缩放与深度无关）。和 weiqi-intro 第一版是同一类，八门 + 锚点门一路绿。没改那支片子，报出来由人定。
weiqi-intro（现版）最大组 0.9%、demo-tls 无，都不报。

**它测的量 vs 提示语让人以为它测的量**（接盲区表）：它测"有一大块在非等比仿射变换下画"，不是"这支片子有没有透视"。
压扁做在着色器里、预渲进离屏 canvas、用 CSS transform，它都看不见；真透视片里另有一块刻意压扁的图解层，它照样报。

### 33. 字体分片来得晚：字不缺，门就是绿的（已修：font_source 判定 6 + loadFonts 按类声明）

**撞到了什么。** weiqi-intro 的 `白子：${n} 口气` 里的 n 是运行时拼的，没列进 `loadFonts`。Noto 子集的数字和空格在 `U+20-7E` 那一片，
这一片要等第一次画到才加载——那一帧用回退字体画，之后才对。这是确定性失败，但：
`font_source.mjs` 绿（它只问"最后是谁画的"，字不缺）；seamcheck 门 1a/2 红，提示语却是"读了时钟/Math.random""存在跨帧状态"——方向错，作者得自己猜。

**修法。**
- `film-assets/scripts/font_source.mjs` 判定 6：初次就绪（`window.ready` + `document.fonts.ready`）之后，某次 seek 让一个 FontFace 从
  `unloaded` 变成加载中，或还有字体文件请求 → 不合格，列出那一刻、那一片、首次由哪些字触发、全片在这一片画过哪些字。
  能按 seek 归属是因为 `FontFace.status` 在 fillText 触发加载时**同步**变（实测：seek 返回前就是 `loading`，请求随后才发）；
  请求只作旁证——按请求归属会错帧。放 font_source 不放 seamcheck：它本来就逐次 seek 记每次画的字和字体栈，能点名是哪些字。
- seamcheck 门 1a/2 失败时加一行 ⚠：初次就绪后有 FontFace 在 seek 期间才开始加载，就说"多半不是时钟/跨帧状态"并指向 font_source。只是提示，判定不变。
- `film-typography` 的 `loadFonts` 文字位置可以按类声明：`[font, { text, sets: ['digits'], ranges: ['U+2460-2473'] }]`（类名见 `CHARSETS`，写错抛错）。
  字符串原样返回，旧写法逐字节不变。代价：整类都会加载、都会逐字核覆盖。**已拷进片子的旧 text.js 没有这个写法**。

**阴性对照**（scratch 夹具，`FILMS_DIR` 指过去）：只列 `白子：口气` → font_source ✗（t=2s 起，首次由 `2␠` 触发），seamcheck 门 1a/2 ✗ 且带 ⚠；
改成 `sets: ['digits']` → 两边都绿。weiqi-intro 副本去掉 allText 末尾的 `' 0123456789'`（还原原缺陷）→ ✗ t=51s 起由 `0␠` 触发；按类声明修好 → ✓。
ghost-jam / demo-tls / weiqi-intro 真实目录三支都 ✓，没有新增报错。

**它测的量 vs 提示语让人以为它测的量**：它测"采样时刻里有没有分片第一次被用到"，不是"全片没有晚加载"——只在两个采样点之间出现的字触发的晚加载看不到（`--step` 越小越全）。

### 36. film-webfx：数组 uniform、只传一次、mipmap / 各向异性（weiqi-intro 作者报告第 5 条，已补）

**撞到了什么。** weiqi-intro 的气泡透镜要传一组圆和线段（`vec4 u_circ[N]`），`setUniform` 只认标量和 vec2–4 / mat3 / mat4，
作者只能绕过封装手写 `getUniformLocation + uniform4fv`；木纹每次 `texture()` 都重新上传，只好挪到加载期调一次；
没有 mipmap，缩小时细线走样。

**修法**（`film-webfx/assets/runtime/webfx.js`，老片钉着旧副本不受影响：_test-webfx / weiqi-intro / weiqi-ch1 的副本都与改前逐字节相同）：
- `setUniform` link 后读 active uniform 反射，数组 / int / ivec / mat2 / uint / sampler 按声明类型分派；旧的几种（float、vec2–4、bool、mat3、mat4）
  仍走原路径，新旧版同一着色器全帧 SHA-256 相同。整个数组少传元素直接抛错——没传到的元素会留着上一帧的值，那是跨帧状态。
- `texture(name, src, { static:true } | { key })`：同一源对象 + 尺寸 + URL（+ key）没变就不再上传。缓存只看内容来源，不看 t。
- `mipmap:true`（WebGL1 非 2 的幂直接抛错，不再"纹理不完整、采样全黑且不报错"）、`anisotropy:n`。

**值得记的一条：只传一次的错用法，seamcheck 是假门。** "源按 t 重画、却声明 static 没 bump key"是**冻结**不是累积：
同一页面里每次都冻在第一次上传那一刻，同 t 两次、乱序、全新页面三种比法比出同一个错结果——阴性对照 seamcheck **全过 exit 0**。
"key 按秒分桶"只有门 2 红（桶内第一次被求值的帧决定内容）。所以单设 `film-webfx/scripts/texcache-check.mjs`：
两个全新页面，一个设 `WEBFX_NOCACHE`（缓存纹理改回每次上传），同一批 t 逐像素比，并报两边上传次数（相同 = 本片没用缓存，门是空的，明说）。
实测：正确用法 24/24 一致（上传 25 vs 48）；改了不 bump 23/24 红；按秒分桶 22/24 红。
这和契约 §2"缓存允许、前提是外部观测不到差别"是同一句话——这道门把"观测不到差别"直接测出来，而不是靠乱序求值间接碰。

**第二条：斜看的平面只开 mipmap 比不开还差。** 1:8 足迹（透视相机下的桌面/棋盘）实测与面积平均参照的 RMSE：
LINEAR 39.1、只开 mipmap 64.9（按大方向选层，另一方向被糊掉）、mipmap + `anisotropy:16` 0.29。
各向同性缩小时 mipmap 本身就够（35.1 → 0.35，平移闪烁 62.6 → 2.6）。和 film-motion 的透视相机配套时要知道这一条。

**它测的量 vs 提示语让人以为它测的量**：texcache-check 测"缓存版与每次上传版在采样到的时刻一致"，不是"缓存键是对的"——
内容只在两个采样点之间短暂变过的抓不到（`--all` 逐帧）。

### 40. 套件只有"单镜头内的运动"，没有镜头之间的语言：转场、共享元素、文字动画都要每支片自己手写（已补：choreo / transitions / textfx）

**这件事是什么。** film-motion 给了弹簧、相机、布局，film-typography 给了拆字和几个入场基元，但"两个镜头之间怎么过去"没有任何东西：
没有时间轴结构（镜头 + 转场），没有转场合成，没有跨镜头的同名元素插值，文字动画只有 drawRiseIn / typedCount / staggerProgress 三个基元。
结果是每支片都在 seek 里手写 `if (t < 3.2) … else …` 的硬切，或者自己写一份叠化；剪辑点是手填秒数，旁白一改就漂。

**修法。**
- film-motion `assets/runtime/choreo.js`（基础集，新片自动拷）：`EASE` / `easeOf` 缓动词汇（**没有默认缓动**，缺了抛错）与 `easeInfo()` 实测；
  `stagger()` 交错编排器（GSAP 语义）；`timeline()` 镜头 + 转场的数据结构——剪辑点 + `align`，剪辑点可以直接是 `vo.at('字')`，`align: 1` = 转场在念到这个字时完成。
- film-motion `assets/runtime/transitions.js`（基础集）：`createStage(canvas, {anchors})`，接口统一成"两个镜头的 paint + 进度 → 一帧"。
  16 种画法：cut / crossfade / dip / wipe（linear / iris / clock / box / bars / custom）/ luma / push / slide / zoom / zoomThrough / whip / glitch / leak / match / magicMove。
  镜头用 `sh.el(name, …)` 登记元素，舞台把框按层的屏幕变换映射后登记进空间锚点（转场里锚点仍是"画在哪"）。
- **Magic Move = 空间锚点的第二个消费者**：两个镜头里同名的元素，morph 路径插值 props（位置/大小/OKLab 颜色/圆角），FLIP 路径重放各自的矢量 draw、plus-lighter 叠化（借 View Transitions）。
- film-typography `assets/runtime/textfx.js`（可选集）：中文正确的拆分（标点挂靠，不单独飞）、入场/出场/强调预设、乱码解码（seeded，乱码池须进 loadFonts）、
  打字机（标点停顿 + 光标）、沿路径、切分揭示、数字滚动、逐字 3D 翻转（透视条带 vs 仿射）、文字 Magic Move。
- 夹具 `tests/fixtures/_test-mg`：14.4 s，12 镜头 11 个转场；seamcheck 门 1a/1b/2/4（全片 432 帧并行）全过。

**撞到了什么：门 4 是唯一抓到它的门。** 第一版离屏层 `imageSmoothingQuality='high'`，门 1a/1b/2（48 个采样）全绿，
`--parallel 4` 报 4/432 帧不同（全在 zoomThrough 窗口）。单页复现：同一 t，前一帧也是 zoomThrough 帧时哈希不同。改 `'medium'` 后 0/432。
采样门的盲区是结构性的：均匀采样里没有两个相邻帧落在同一个 0.6 s 转场窗口里，而这个泄漏只在"连续两帧都在做大缩放 drawImage"时出现。
**推论**：用了 transitions.js 的片子，seamcheck 应带 `--parallel`（accept.mjs 的 seamcheck 门目前不带）；场景自己在 seek 里设 'high' 缩放 canvas 源的，同样中招。

**静帧看出来、门看不出来的三处**（都修了，都是"看了图才知道"）：甩镜拖影第一版是 10 道分离的边；匹配剪辑让 B 缩小、四周露黑边；
噪声溶解粗颗粒 + 亮烧边被用户看小样指出"像廉价转场"——烧边宽度/亮度从此是必填参数，代价表写清"粗颗粒/亮边什么时候值得"。

**它测的量 vs 提示语让人以为它测的量**：Magic Move 的配对只按名字——名字相同的两个无关东西也会被插值，所有门照常绿；
转场期间登记的锚点是"画在哪"，被遮罩擦掉的那一半照样有框（遮挡门/出画门在转场窗口里的结论要打折）。

**没做**：透视转场（立方体、翻页）；任意路径形状插值；accept.mjs 的 seamcheck 门不带 `--parallel`（INTEGRATION 范围外，建议由维护 accept.mjs 的人决定）。

**第一支用上它的片子：`films/weiqi-fx-eyes`**（weiqi-ch1 第 4 课 d4–d8 重做）。accept 7 道适用门全绿（seamcheck / relaunch / shotlist / facts / fontsrc / check / verify）。顺带撞到两件，都是套件层面的：
1. **"文字"锚点同名取外包会制造遮挡门假阳性。** 场景把每段画面文字都登记成「文字」，按 ARCHITECTURE §10 第 2 条取外包：顶部读数 ∪ 盘下的「眼」= 一个跨过整块棋盘的大框，
   遮挡门报 639/885 帧"盘线压字"。weiqi-ch1 的 critique 块写的就是 `against: ["text", "文字"]`，它没撞上只是因为它的字都在顶部文字带里。
   契约是对的（同名 = 同一个东西），坑在"文字"这个名字诱导人把所有字登记成一个东西。建议 film-critique 文档在遮挡门处点一句：文字要么只用 fillText 拦截（`text`），要么每段字各起名字。
2. **转场里镜头被画在离屏层上，场景直接 `A.box()` 登记的框是"没转场时的位置"。** weiqi-fx-eyes 第一版的盘线框就这样在 zoomThrough 窗口里记小了；改走 `sh.anchor()` 后由舞台按层变换映射。
   transitions.js 的注释和 references/transitions.md §2 已写，但老片子迁到舞台上时最容易漏。

### 41. 套件没有三维：用户要"3d 能力、特效、镜头变换、高级感"，最省事的写法（three.js 原样 + 网页惯用法）每一处都违约（已补：film-webfx 三维）

**撞到了什么。** 用户原话："我觉得需要 3d 能力，以及加特效，加比如镜头的变换……有那种玄幻的或者像是黑客帝国的那种高级感。"
film-webfx 只有全屏片元层（webfx.js），SKILL.md 对 three 的说法是"没装、没复测、旧调研说能 seek"。
而网页上做三维的惯用写法——`renderer.setAnimationLoop`、`Clock.getDelta()`、`EffectComposer.render()`（不传 delta 就读它自己的 Clock）、
粒子 `p += v·dt`、`MathUtils.randFloat`——**每一条都违反帧契约，而且大多是静默的**：`getDelta()` 照常返回一个数，片子每次渲得不一样。

**修法。** film-webfx 加五个随片运行时 + 两个工具（只改 film-webfx；老片不受影响）：
- `three-film.core.js` / `three-film.module.js`：three.js 0.186.1（MIT）的**帧契约版**，`scripts/vendor-three.mjs` 生成。
  `Clock`/`Timer`/`setAnimationLoop`/`compileAsync`/`Math.random` 系列（共 30 处）用到就抛错，uuid 改计数器，Loader 缓存回调改微任务。
  补丁按精确文本 + 次数匹配，上游一变脚本失败退出。selfcheck 第 8 项照常过。
- `stage3d.js`：`S.frame(t, paint)` = 复位 → paint → 结构检查 → 渲染 → 锚点。**每帧先把场景树复位到 `freeze()` 的静止姿态**（Theatre.js "没上时间轴的属性取静态值"）。
- `camrig.js`：样条（按弧长）、环绕、推拉、俯仰、跟随（对过去轨迹加权平均，不积分）、焦点切换、哈希手持；`fromCamera3d()` 与 film-motion camera3d 等价（逐点差 ≤ 1.1e-12 px）。
- `post3d.js`：HDR RT 串的后期链——泛光（Jimenez 13 tap 多级）、景深（Gustafsson 单遍）、体积光（GPU Gems 3）、色差/颗粒/暗角/扫描线/故障合成一遍（pmndrs EffectPass 的思路）。风格参数每帧全量、无默认值。
- `particles3d.js`：闭式粒子（GPU 顶点着色器 / CPU 两种），`lifecycle`/`rebirth`/`drift`。
- `scripts/bench3d.mjs`：每一样东西在 1080×1920 / 1920×1080 下的每帧毫秒。

**值得记的一条：保留式场景图让"漏写一个属性"变成只有门 2 抓得到的跨帧状态。** 阴性对照 `tests/fixtures/_test-3d/scene-bad-noreset.html`

### 43. 门从"有文件就跑"改成"片子声明了才跑"；老片钉住口径；三个判定 bug（已改）

**这件事是什么。** 套件的门原来按"前置条件存在就跑"决定适用：有 facts.md 就对账事实，有 shotlist 的 json 块就查分镜和发散留痕，
有 scene.html 就跑 check.mjs 的全部子判据（可读性、WCAG 对比度、事实数字、事件对点……）。但那些文件多半是**脚手架写的模板**，
不是作者要这道门的声明。结果是一支完全守契约、只是不是解说片的片子，首跑就红一片：scratch 探针片（瓦片地图 + 精灵表 + 小 ECS，无旁白）
seamcheck 五门全绿，check.mjs 4 个 FAIL（脚手架自己写的 script.json 没有 narration.json、手机 360px 观看宽、
暗色游戏 HUD 的对比度——**没有任何开关能关**、分数计数器被当成 38 个找不到出处的事实），accept 的 shotlist 门因为模板里自带 1 个 shot 而 exit 2。
套件的主张是"skill 呈现能力，不规定风格"，可门在默认值里替片子规定了"你是一支给手机看的中文解说片"。

**改成两类门**（KERNEL.md §4、accept.mjs 头注释）：

| | 门 | 什么时候跑 |
|---|---|---|
| 内核门 | seamcheck（含门 4）、relaunch（门 5 对账）、physcheck、fontsrc | 永远开，前置条件在就跑——它们守的是 seek(t) 契约，不守就渲坏 |
| 可选门 | shotlist、facts、check、verify | 本片 film.json `checks` 声明了才跑；check 门另认 critique 块里写的本片法律 |

`checks` 的形状：`{ "shotlist", "divergence", "facts", "verify": bool, "critique": { 子判据: true | 参数 } }`。
check.mjs 的 15 个子判据（`narration mp4 truepeak loop readability contrast facts style_guide laws still empty marks claims tilt page`，
表在 `film-critique/scripts/_film.mjs` 的 `CRITIQUE_CHECKS`）**声明了就照原来的严格度判，不降成提醒**——第 23 条的教训是
"FAIL 被关掉之后缺陷还在"，降级会重演它。没声明 critique 的片子只查 laws / loop / page（本片法律、循环接缝、页面报错），
报告里列一条 `SKIP checks` 写明哪些没开；子判据名字写错直接退出（拼错 = 静默不开，是最坏的那种）。
对比度现在可以关，也可以改阈值：`"contrast": { "min": 3, "large": 2, "large_px": 24 }`。
发散留痕（讲法 / 视觉方向 / 近作对照）由 `checks.divergence` 开，默认不开；第 27 条"讲法整节没有将来升为失败"的计划随之作废。

**老片钉住口径，像运行时一样。** 改默认之前先跑 `film-production/scripts/pin-checks.mjs`：按**改造前**的判定规则
（旧 accept 的 hasJsonBlock、facts.md 存在、narration.json 存在、check.mjs 全开）把每支片子（含夹具）当时适用的门显式写进它的 film.json，

**脚手架瘦身。** `new-film.mjs` 默认只建内核骨架：film.json（`"checks": {}` 明写而不省略——省略的字段没人知道它存在，第 17 条）、
scene.html、runtime/，不写任何文档。`--recipe explainer` = 原来的全套模板 + script.json + 声明全套检查；
`--with narration` / `--with facts` 只要其中一部分。

**accept 缓存按门取。** 旧键里的"套件哈希"是整个 skills/ 下所有脚本：加一个和老片无关的适配器，所有片子的所有门都重跑（weiqi-ch1 单门半小时）。

**selfcheck 第 8 项只查套件自己写的运行时。** 第三方库列在 `<skill>/assets/vendored.json`（必须写 upstream 和 license，列了但文件不在算不合格），
不做词法禁令。理由：违约只在 seek 期间有害，而那一段由逐片 seamcheck 探针（seek 期间统计禁用 API）和门 1a/1b/2/4 在像素层判；

**顺手修的三个判定 bug**（来自做片 agent 的报告；都只会把假 FAIL 变成 PASS，不会把 PASS 变成 FAIL）：

1. **`mark.sync` 一律取全片第一次出现。** MARK 绑的是后一句里的「下进去」「禁入点」，前一句先念过一次，就会拿十几秒前那次去比，报假错位。
   现在按 MARK 声明的上下文取：`nth` > `line`（哪一句）> 离事件最近的那一次，说明里写取的是第几次。
   只出现一次的词结论和说明都不变；出现多次时，"最近的那一次"的距离不会比"第一次"更远，所以过了的照样过。
2. **`mark.visible` 只比区间起点前一帧和中点。** 短促的变化（闪一下、中点前已复原）被判"声明了但没画出来"。
   现在区间内按成片帧栅格最多取 24 帧（总含中点），取变化最大的那一帧，够 4 像素就停。
3. **遮挡门把被裁到画面外、看不见的部分也算压字。** 锚点和文字框按契约不裁剪（出画门要靠它），遮挡门却直接拿未裁剪的框求交。
   现在两边都先裁到画面内，整个在画面外的不参与比较；出画门照旧用未裁剪的框。
   顺带改正 checks.md 的一处文档：只对 text 判、一段字都没截到时代码一直是 FAIL，文档写成了 SKIP。

**前后对账**（`accept.mjs --fixtures`，前一遍允许缓存，后一遍 `--no-cache`）：**24 支 × 8 门 = 192 格，0 格不同**（含 9 个夹具；13 处 ✗ 两边逐条相同，包括 eval-clearing / eval-deepsea 的发散留痕失败——它们被钉成 divergence: true，照旧报红）。

weiqi2-l1 / l2 / l3 / l4、weiqi2-open）只差在 mark.sync 的 PASS 说明多了一句"词在旁白里出现 n 次，取第 1 次"，结论全部相同——
这些词都出现多次，但每支片子的 MARK 恰好绑在第一次上，所以修 bug 1 没有改变任何一支老片的结论。三个 bug 的改前 / 改后用一个合成夹具对照过
（trial 目录，不进仓库）：MARK 绑第二次出现的「下进去」，旧版 FAIL 差 10.60s → 新版 PASS（取第 2 次）；只在 5.0–5.1s 闪一下的事件，旧版 mark.visible FAIL → 新版 PASS；

**最小新片**（`tests/fixtures/_test-kernel`：`new-film.mjs` 默认骨架，只有 seek、无旁白、无文档，`"checks": {}`）：渲一次后 accept——
seamcheck（含门 4）✓、relaunch ✓、fontsrc ✓，physcheck / shotlist / facts / check / verify 全是 `–`。新片不被逼着写文档。

**顺带查清的一处红：weiqi-ch1 的 seamcheck ✗ 是 accept 的超时，不是片子的缺陷。** 上一轮起 accept 对带离屏合成运行时的片子自动开门 4，
weiqi-ch1 是第一支真跑门 4 的长片（7507 帧：全片顺序截一遍 + 4 页并行截一遍）。单独跑 `seamcheck --film weiqi-ch1 --parallel 4`：
**门 1a / 1b / 2 / 4 全过，7507 帧 0 帧不同，探针无违约**，耗时约 42–60 分钟（和别的验收进程抢 CPU）。而 accept 每道门的上限是 30 分钟，到点被杀；
execFileSync 抛 `code: 'ETIMEDOUT'`、status 1、输出里没有"失败/✗"字样，于是表上只剩一句"退出码 1"，看着像片子不确定。
改造前后两张表里它都是这个原因，所以逐格一致。修法：accept 认出 ETIMEDOUT 时写"超时（N 分钟）被杀：门没跑完，不是判了不合格"；
逐帧扫全片的门（带 --parallel 的 seamcheck、relaunch、check）按帧数放宽上限（帧数取渲染清单，否则按旁白时长估；每帧 1 s / 1 s / 0.4 s + 10 分钟，至少 30 分钟），
`--gate-timeout <分钟>` 统一覆盖。

**它测的量 vs 提示语让人以为它测的量**：可选门的 `–` 现在有两种含义——"前置条件不在"和"本片没声明"。
`–` 从来不是"过了"；没声明的门没人查，验收表绿了只说明内核契约守住了、以及片子自己要求的那几道门过了。

  （143.0.7499.4 / 145.0.7632.6 / 151.0.7922.34 / 156.0.8078.4），
  于是"要第二个 Chromium 版本才能测"这个前提自己就成立了。
  按**真实渲染路径**（整片 313 帧渲成 mp4，不是 seek 几个时刻）实测：

  | 轴 | 结果 |
  |---|---|
  | 版本：headless shell 143 / 145 / 151 / 156 | 成片**逐字节相同** |
  | 版本：完整 Chrome 143 / 151 / 156 | 逐字节相同；145 例外，差异低于可见阈值 |
  | **构建形态**：同为 156 的 headless shell vs 完整 Chrome | **差 5.4–13.6% 像素，最大 216/255，肉眼可见** |

  **真正看得见的差异不在版本号上，在构建形态上**，而这条轴原来是隐形的：
  Playwright 默认用 `chromium_headless_shell-*`，手动指定路径很容易拿到
  `chromium-*/Google Chrome for Testing`（完整 Chrome），
  **两者 `browser.version()` 返回同一个字符串**，只有 CDP 的 `product` 能分开，
  于是指纹分不出、漂移告警漏报。现在指纹带上形态了。
  看得见的差异来自等宽字体回退选了不同的字。

  所以钉**版本**是为了哈希缓存和可复现性（版本变 → PNG 字节变 → 逐帧哈希全失配 →
  缓存整体作废，而画面一模一样），钉**构建形态**才是为了视觉保真。两件事不能混说。

  **这段测量错了三次，每次都是测量工具污染了被测对象，这比结论本身值钱。**

  1. 第一遍比 `locator.screenshot()` 出来的 **PNG 文件 md5**，得出"版本两两 5/5 帧全不同"，
     并且已经据此对外说了"钉版本是必要的"。解码成 raw RGB 再比：**0 个像素不同**。
     两个 PNG 确实是不同文件（138382 vs 138386 字节），但不同的是容器编码。
     **判据不能是 PNG 字节。**
  2. 第二遍改成直接读 canvas 的 `getImageData`，得出"143 vs 145 只有一帧差 3/255"。
     但 **`getImageData` 回读本身会改变后续帧的像素**（疑似 canvas 被降级到 CPU 光栅）：
     同一浏览器，每帧回读 vs 不回读，从 t=3 起差 4.4–11.9% 像素。
     **回读是观测手段，却改变了被观测的东西。** 第一帧回读还没生效，
     那里两套测法完全对得上（都是 276 px、最大 3/255、全在 y=1478）——
     正因为对得上，才更容易误以为整组数据都可信。
  3. 两遍用的都是**渲染管线从不使用的那个二进制**。测了一个不在生产路径上的对象。

  合起来是一句话：**先确认你测的是不是生产路径上的那个东西，
  以及你的测量手段会不会改变它。**

  **查这条轴的时候撞见两个没查出原因的异常，必须留着，不要因为"复现不稳"就不写：**

  - 旧版 headless shell（143、145）9 次截图里有 **2 次从第二帧起整屏全白**，且不报错。
  - 完整 Chrome 156 有 1 次整片渲染，**连续 3 个分片（第 150–239 帧）与另外 6 次不同**，
    差 5.7–6.1% 像素、最大 42–174/255——这是肉眼可见的量级。

  默认路径（headless shell 156）10 次整片渲染全部一致，所以生产路径目前看是稳的。
  但这两条指向同一件事：**存在跨启动的非确定性，而 `seamcheck` 结构上抓不到它**
  ——它的三道门全在单个进程内，门 1b 的"全新页面"也还是同一个浏览器进程。
  这是第四个盲区的候选，只是还没有可靠复现，所以没写进上面那节。
  要抓它需要"同一片子渲 N 次比成片 md5"这种跨进程的门，成本高，没做。

  没关掉的是另一条轴：所有构建都跑在同一台 macOS、同一个 SwiftShader 软件渲染下。
  **换 Linux（FreeType 字体栈）或换真 GPU 会怎样，仍然不知道。**
  而且缓解措施里有一条**在这台机器上是空的**：
  `--font-render-hinting` 在 macOS 上完全无效。
  demo 片 5 个时刻 none/full 哈希全同；换成 DOM 文字（Georgia 17px）
  再测 none/full/medium 三档，三档哈希也全同——说明不是"canvas 文字用不到它"，
  是 **CoreText 不做 hinting，这个标志在 macOS 上整体无效**。
  它是给 Linux 买的保险，而 Linux 正是测不到的那一侧。
  **连买的保险有没有用都没法在这里验。**
- ~~`renderer` 版本不一致的警告分支：要装第二个 Chromium 版本才能触发，没测~~
  **已端到端触发。** 用 shell 143 渲并 `--pin-renderer`，再用默认浏览器渲：

  ```
  ⚠ 本片记录的渲染环境与当前不同：chromium "143.0.7499.4" → "156.0.8078.4"。
    像素可能与当初不同，重渲后重跑 seamcheck 并重看静帧（确认后 --pin-renderer 改记）。
  ```

  指纹加上形态之后，同版本换形态也抓得到了（`"156.0.8078.4" → "156.0.8078.4 (full Chrome)"`）——
  这正是原来会漏报、而且是唯一肉眼可见的那一类。
  顺带确认分片缓存换版本后**没有错误复用**：带 143 的缓存用 156 渲，11 片全部重编、0 片复用，
  成片 md5 与 143 的逐字节相同。因为哈希比的是截图 PNG 字节，
  字节相同就意味着像素相同，**构造上不可能"哈希对上、像素不同"**。
  代价是白干：143→151 之间 PNG 编码器变了，像素一样但字节全变，于是整体重编。
- ~~音频读音没有自动手段，只能人听~~ **第四种方法成功了，而且推翻了成片。**
  这是整个项目里方法学教训最密集的一条，值得完整留着。

  前三种全失败，每种都是被对照或检验力拆穿的：

  | 方法 | 想判什么 | 怎么失败的 |
  |---|---|---|
  | 波形差分 | 词典是否被采纳 | 同一请求连发两次差异同量级；故意写错的词典反而离不带词典最近 |
  | MFCC-DTW 比对参照音 | 念 yuè 还是 yào | 方法学对照失败：强制 `(yin2)(xing2)` 的版本测得更接近 háng |
  | token 时长统计 | 词典是否被采纳 | N=6 时「钥」中位差 60ms、p=0.064 看似将显著；**补到 N=12 后中位差 5ms、p=0.269，效应消失** |

  第三条值得单记：停在 N=6 就会报出假阳性。**p 在边缘是检验力不足，不是阴性结果**，
  该做的是补样本而不是二选一地解读。

  **第四种成了：只量「钥」那一个字的共振峰（LPC 极点法，F1 的 p80）。**
  前三种都栽在同一件事上——拿**整词的谱距离**去判**一个音节的元音**，信号被淹了。
  yuè 的 /ye/ 和 yào 的 /iɑu/ 在 F1 上差得极大，换成针对性的量就分得开了。

  成功的那次多做了三件前三次没做的事，这三件才是可迁移的：

  1. **先建检验力闸门，再看目标。** 用同一音色同一语境句合成两组参照各 12 次
     （密月/蜜月/密阅 vs 密药/秘药/密耀），预先写定判据 p<0.001 且留一法 ≥23/24。
     实测两组 F1_p80 **完全不重叠**（305–409 Hz vs 500–722 Hz，U=0，p=3.66e-05，d=5.22）。
     闸门过不了就该直接报"第四种也失败"，不去碰目标数据。
  2. **做正对照，而不只是带/不带的对照。** 只比"带词典 vs 不带词典"有个致命盲点：
     **引擎默认读音恰好等于词典读音时，永远测不出差别。** 所以要故意把本来读对的词掰错
     （`密月/(mi4)(yao4)`）看它翻不翻。结果 8/8 没翻——这才证明是词典无效，不是没差别。
  3. **作废不该解读的数据。** 「银行」那组正对照测出 F1 在 1100 Hz 上下，
     物理上不可能是 F1（鼻韵尾导致），这组没过闸门就不解读，而不是硬解释。

  **结论有行动后果，不只是一个数**：拼音写法的发音词典在 seed-tts-2.0 + 云舟上
  **静默无效**（接口不报错），SSML `<phoneme>` 也无效，三条本该改读音的条目共 28 次合成 0 次生效；
  **只有同音字文本转写（`密钥/密月`）有效，12/12**。
  于是 `demo-tls` 的成片里「密钥」一直念的是 **mì yào——念错了**，
  而 `script.json` 里那条词典从头到尾没起过作用。
  `tts.py` 的 `lint_dict` 原来只校验**格式**，格式合法的无效条目照样放行，
  现在会对拼音条目直接告警并建议改用文本转写。

  仍然关不掉的：只差声调、或带鼻韵尾的读音对过不了这个闸门，还得人听；
  结论只在这一个音色上测过。音色好不好听、响度听感，仍然是人的事。
- ~~增量重渲只做了一半~~ **已完成。** 关键是搞清楚贵的不是截图（CDP 之后 90+ 截图/秒），
  是**编码**（x264 slow 干净画面约 180 fps，满屏噪声只有约 8 fps）。所以要跳过的是编码。
  我最初的方案有一处硬伤——"截完一片再决定喂不喂 ffmpeg"，那时帧已经扔了。
  film-motion 改成**边截边逐帧比哈希**，全片对上就复用缓存的分片 mp4，
  第一次对不上就从片头重截（`seek` 是纯函数，重截即原帧）。不用缓冲 PNG，最坏多截一片。
  分片边界改成绝对帧号的整数倍（默认 1 秒），所以区间渲染也能复用全片留下的分片。

  我在 demo-tls 上独立复现（和它的测试片不是同一支）：
  ```
  真冷启动   313 帧 4.1s   分片：编码 11 / 复用 0   md5 73b1b1a3…
  再渲一次   313 帧 2.9s   分片：编码  0 / 复用 11   md5 73b1b1a3…
  --no-cache 313 帧 4.0s   分片：编码 11 / 复用 0   md5 73b1b1a3…
  ```
  **三者 md5 完全相同——不只是解码后逐帧一致，是字节一致。** 比它报的还强。
  我担心的两个坑（concat 混合来源的时间戳/关键帧、tmix 跨片）实测都不存在：
  每片单独起 ffmpeg，tmix 只在片内平均，分片边界总落在两个输出帧之间。

  仍未解决：缓存不自动清理（每种编码参数组合各留一份，只能靠 `--clean-cache`）；
  没测过换机器、x264 线程数不同时输出是否仍逐字节一致——若不一致，
  复用的分片内容仍正确，但"复用等于重编"不再严格成立。
